## 四、游戏状态机与页面路由

`main.js` 维护 `state.screen ∈ {start, map, game, shop, skins}`，`#app` 内整体替换子树；游戏内再叠加结算弹窗层。

单关运行时状态机（`js/game/session.js`）：
```
SELECTING ──(点击结账/倒计时归零)──> CHECKOUT ──(弹窗动画结束)──> RESULT
   ↑                                                              │
   └──────────────(失败→再来一次) / (成功→下一关或回地图) ───────────┘
```
- **计时器**：进入 SELECTING 即启动；`remaining ≤ 30s` 时状态栏变红闪烁；归零 → 自动以当前购物车结算（空车则 T=0 → Q=100% → 0 星）。
- **超支拦截（关键）**：每次点击商品即计算 `T + price`；若 `> budget` 则不加入购物车，商品卡执行抖动弹回动画 + 轻提示「超支啦！再看看别的吧」。
- **CHECKOUT**：暂停计时（方案要求），冻结选品交互，结算并展示弹窗。
- **延时卡片**：仅 SELECTING 可用，每关上限 3 张；使用后 `remaining += 30s` 并播放「+30s」飘字。

### 5.3 尾数允许集合与预算取值
```
TAILS = { int:[0], half:[0,50], half_nine:[0,50,90], mix99:[0,50,90,99] }   // 单位：分
```
- 先由尾数集合枚举出 n 件可实现的尾数和（mod 100）集合 `T*`（n≤4，暴力枚举，开销可忽略）。
- 从 `budgetRange ∩ {t ∈ T*}` 中随机取一个 B（分）。例：第 7~13 关 n=2、tails{0,50} → T*={0,50} → B ∈ {10.0, 10.5, ..., 25.0}。

### 5.4 商品池抽取
1. 按当前关卡品类约束，先分配**精准解**所需品类的商品（从 `items.js` 中该品类随机抽，全部去重）。
2. 计算每层（4 位）品类归属：层 0→饮品、层 1→零食、层 2→日用品，第二页层 3→调味品、层 4→饮品、层 5→零食；层内先放精准解商品，再用该品类干扰项补齐。效果贴合参考图的「一行一品类」。
3. 干扰项数量 = 件数 − n。同一关卡内**不得出现重复商品**（94 个商品名均唯一，天然满足）。
4. 若某品类商品不足以填满层位，则从其它品类补位（保证总件数不变）。

### 5.5 精准解定价（水填充，保证 Sum = B）
```
splitBudget(B_total, n, tails, band):
  1. 暴力枚举尾数计数 (c0,c50,c90,c99)，Σc=n 且 Σ(c·tail) ≡ B_total (mod 100)
     → 得到每件的尾数 t_i
  2. rem = B_total − Σt_i          // 必为 100 的整数倍，且 rem ≥ 0
     把 rem/100 个「整元」分配给 n 件：w_i 使 p_i = w_i·100 + t_i ∈ band
     - 目标区间 [lo_i, hi_i] = [floor(0.8B/n), ceil(1.2B/n)]
     - 品类软约束：若与品类参考价有交集则取交集
     - 水填充：每件先取 lo_i，余量按「最低于 hi_i 者优先」随机分配，直至 Σw 用尽
  3. 返回 p_i；若任一步不可行 → 外层换 B 重试
```
- 尾数分配让 `.5/.9/.99` 自然出现在商品标价上，且总和精确等于预算（3 星可达）。

### 5.6 干扰项定价
- `avg = B/n`；干扰项价格 = `rand(0.6×avg, 1.5×avg)`，clamp 到品类参考价，最低 ¥1.00，并按尾数类型补齐尾数（如 ch2 只允许 .0/.5）。
- **启发式避雷**：候选整数价格中优先排除与任一精准解价格 ±1 以内者，显著降低重试率。

### 5.7 唯一性校验（核心）
```
uniqueExactSolution(pool, n, constraint, B):
  count = 0
  for comb of combinations(pool.indices, n):
     if !satisfiesConstraint(comb, constraint): continue
     if Σ price == B: count++ ; if count > 1: return false
  return count == 1
```
- 另统计 `nearCount` = 满足约束且 `0 < B−Σ ≤ 10%·B` 的组合数，要求 `nearCount ≥ 1`（保证 1/2 星可达；这也是 2 星的合法路径）。
- **复杂度**：商品池上限 24 → 最坏 `C(24,4) = 10,626` 组；品类约束下组合数更少（第 24~26 关「四类各选1」为各品类件数之积，约 6⁴=1296）。单次校验 < 1ms，300 次重试亦在数十毫秒内。
- 枚举用递归 + 剪枝：按品类约束预先分组，只在允许的品类里选取，避免无效组合。

### 5.8 生成流程与重试兜底
```
for outer in 1..20:                 // 换预算重试
  B = pickBudget(range, tails)
  for attempt in 1..300:            // 换池/换价重试
    pool = buildPool(件数, 约束)      // 抽商品、组层
    assignSolutionPrices(pool, B, n)  // 水填充
    if 失败: continue
    assignDistractorPrices(pool, B, n)
    if uniqueExactSolution(pool, n, 约束, B) && nearCount >= 1:
        return { levelId, B, n, 约束, items: pool, solutionKey, seed }
return fallbackFixedLevel(levelId)   // 极端兜底：返回该关预置的手工关卡（写在 levels.js 里）
```
- 实际重试率极低（几千分之一），且 `MAX` 总量封顶，**不会死循环**；兜底静态关卡保证永不空白。

### 5.9 换题与固定题
- 进关时：若 `levelStars[levelId] === 3` → **每次进关都重新出题**（保留章节参数，新 seed），不落 `fixedQuestions`。
- 若 `< 3` → 首次进入时生成并写入 `fixedQuestions[levelId]`，之后**始终复用存档中的题**（"补考"）。
- 出题完成后立即持久化，避免刷新丢题。

## 六、规则实现要点（`js/game/rules.js` 纯函数）

| 函数 | 说明 |
|---|---|
| `starOf(T, B)` | `Q=(B−T)/B×100`；`Q=0`→3星；`0<Q≤5%`→2星；`5%<Q≤10%`→1星；`Q>10%`→0星 |
| `coinsOf(T, B, star, clearIndex)` | 仅 1/2 星发放：`ceil((B−T)/100)`（元）；再乘递减倍率 |
| `decayMul(clearIndex)` | 第1~5次 100/80/60/40/20%，第6次及以后 0% |
| `chapterUnlocked(ch)` | 门槛 `[—, 12, 26, 41]`，用历史最高星之和判定；锁定页不消耗星星 |
| `skinsUnlocked(threeStarCount)` | 购物车：银(0)/草莓粉(3)/机甲灰(10)/黄金闪光(20)；存钱罐：小花猪(5)/太空猪(15)/招财金猪(25) |
| `resultText(star)` | 鼓励话术（0 星失败、1/2 星、3 星完美），文案集中在 `js/data/i18n.js` |

## 八、关键边界情况与坑

1. **超支拦截时机**：在 `click` 事件内先算 `T+price > B` 再决定是否入库；拦截路径不得写入任何状态（避免"抖动了却已加入"）。
2. **超时自动结算 vs 手动结算竞态**：用 `session.state` 单一真源守卫 —— 进入 `CHECKOUT` 后立即 `clearInterval` 并置 `state='checkout'`，任何后续计时回调/点击回调直接 return。
3. **空车超时**：T=0 → Q=100% → 0 星失败，弹窗按钮为「再来一次」，不影响 `clearCounts`。
4. **回刷换题 vs 未满星固定题存档冲突**：以 `levelStars[levelId] === 3` 为唯一判据；一旦某关升到 3 星，立即从 `fixedQuestions` 中清除该关题目，之后每次进关重新生成。
5. **递减计数器记账**：只在成功结算（星≥1）时 `clearCounts+1`；`clearCounts` 决定本次倍率时，**用递增前的值**（第 1 次 = 100%）。
6. **ceil 取整表现**：`B−T` 在尾数定价下常见 10~99 分 → `ceil` 恒为 1 元；`B−T` 为整元时取原值。玩家体验为"接近预算 → 得 1~2 元零花钱"，与「零花钱攒够 10 元换 1 张延时卡」的节奏一致。
7. **精准解唯一 vs 视觉可辨识**：品类软约束可能导致某品类价格被迫贴边（如第 26 关 B=50、n=4 时饮品只能取 10.00），此时以占比区间为准、放宽品类参考价 —— 需在校验中显式允许。
8. **两页同时选中**：翻页只改 `shelf` 的平移量，不动 `session.selected`；已选商品卡的"变暗"状态跨页保留。
9. **双击删除 vs 单击**：购物篮缩略图上绑定 `dblclick` 删除；同时用 ~250ms 计时器抑制单击副作用（购物篮内单击不触发任何事，天然无冲突）。
10. **38MB 素材**：`loading="lazy"` + 仅渲染当关商品；商品图统一 `object-fit: contain` 于虚线框内，避免不同留白导致的视觉跳动。
11. **浮点误差**：所有金额以「分」为整数存储，仅在渲染时除以 100 格式化 —— 杜绝 `0.5` 相加变 `0.4999` 导致 3 星判定失败。
12. **中文文件名**：`encodeURI` 处理；若 `file://` 下个别浏览器异常，改用 `python3 -m http.server 8000` 即可（README 不另建，直接口头告知）。

## 十一、实现补充说明（编码期发现的数学约束，已按最小偏差处理）

**占比区间（相对容差 rel）升级机制**：5.2 节的 `band(n)=[0.8/n,1.2/n]`（n=2 时 40%~60%）在**第一章 n=2 且预算 8~21 元**的场景下被证明不可满足：
- 整数尾数下，`n=2` 时单品价格只可能落在 `[0.4B,0.6B]`，即一段宽 `0.2B` 的整数区间；预算 8~21 → 仅 2~4 个可选整数价格；
- 精准解两件必须取走其中 2 个价位，而「不得产生第二个 Sum=B 组合」要求**这两个价位在池中唯一**，池中剩余干扰项只能取区间内其它价位 → 池件数 4 时必然出现重复价位 → 必然产生第二个 Sum=B 组合（如 B=12 时 `6+6=12`）。故该区间下**第一章 n=2 关卡无解**。

处理：取价区间按**相对容差 rel**（`band(n) = (1/n) × [1−rel, 1+rel]`，即上文的 `[0.8/n,1.2/n]` 恰为 `rel = 0.2`）实现，编码时按 `rel = 0.2 → 0.25 → 0.3 → 0.4` 逐步放宽，**优先使用最窄的可行情**，即只有数学上不可行时才放宽。此改动同时满足「保留 n=2」与「占比随 n 自适应」两条已确认决策，且不放宽任何已达成可行解的关卡。
（注：此处为**相对容差**，即区间宽度随 `1/n` 等比缩放；早前表述中的绝对 δ 写法有误，已更正。）

**1/2 星可达性**：整数尾数下 `Q≤10%` 等价于 `T ≥ 0.9B`，而 `T=B-1` 需 `B ≥ 10` 才落进该区间。因此：
- 校验项 `nearCount ≥ 1`（存在 `0<Q≤10%` 的可选组合）保持为**硬性要求**，但在极端关卡允许在耗尽重试后降级为软要求，以避免死循环。
- 第一章 8~9 元预算的关卡（若命中该预算）实际只可能拿到 0 星或 3 星，属文档参数的自然结果，不做人为修饰。
